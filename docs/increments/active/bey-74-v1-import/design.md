# Import from the old platform

Status: in progress, 7 October 2026. Tracked in [BEY-74](https://linear.app/beyondpilot/issue/BEY-74) (startups) and [BEY-75](https://linear.app/beyondpilot/issue/BEY-75) (use cases). It carries out the [migration from v1](../bey-22-phase-1-domain-model/design.md#migration-from-v1) of BEY-22 against the real export, and uses the [review lifecycle](../bey-76-review-lifecycle/design.md).

## Source

GenAI Fund's export `genai_matching_db_export_2026-10-04-2.xlsx`, two sheets, each with a title and a note above the header on the fourth row:

| Sheet | Records | Holds |
| --- | --- | --- |
| Startups | 2,426 (2,125 active) | Company facts, product fields, links to decks, demos and logos on `papi.genaifund.ai` |
| Use Cases | 233 (218 approved) | Title, description, content, tags, price, deadline, the enterprise's id, name and industry, the creator, links to attachments |

The file holds names and email addresses, so it is never committed. It has no users, proposals or matching decisions. The attachment links answer without a session.

## Decisions

1. **A one-off load, not a feature.** The brief asks for a migration that reconciles with its source (§11), not for an import function; the export it asks for (§7.10) is operational reporting and comes separately. The records are written once, so the application gains no import module, endpoint or operator method that would have to be removed after the cutover.
2. **A script writes the database.** `infrastructure/legacy-import/` reads the workbook, maps the values, fetches the files and writes one SQL file and a folder of files. Its rules are code in the repository; the workbook, the SQL and the files it produces are not. The SQL runs in one transaction under the database's constraints; the search index is then rebuilt from Admin › AI, since no event is published. The audit log records nothing of the load: its catalog is closed, and an action it does not know would break the log's reading; the dump taken before the load and the build's report record it instead.
3. **Imported, not approved.** GenAI Fund has not said how it wants the old records reviewed (BEY-41), so an organization and an active startup's solution arrive `in_review`, an inactive startup's solution and every use case arrive `draft`. A solution is not listed. An organization has no member and is created by the operator account of the environment. Nothing imported is public until an operator approves it. On staging alone, `staging_list.py` then approves the organizations and approves and lists every imported solution, so matching is built and tried on real data (Đạt, 7 October 2026); production keeps them in review.
4. **Staging first, then production.** The load runs on staging; test records and duplicates are removed there with SQL that is kept with the script. Production receives the same load and the same removals, after a dump of its database.
5. **A use case belongs to programs.** 167 use cases carry a program tag in v1. `usecase` stores `use_case_program (use_case_id, program_id)` and depends on `program`; an operator sets a use case's programs, and the public list narrows by program, so a program page reads its use cases from `usecase` and `program` does not depend on `usecase` ([brief §9](../../../brief/BeyondPilot-Vendor-Product-Brief-and-Scope.md#9-example-operating-scenario): a campaign has linked use cases). This is the one change to the application. Nestlé Vietnam AI Reinvention, which only v1 names, is created as a draft program; its details wait for GenAI Fund.
6. **Values are mapped, not copied.** Solution types to focus areas, industries to industry codes, product stage to maturity, country names to ISO codes, `|||` and comma lists split, empty strings and "Not specified" to null. A startup named as a test, a startup with a `test.com` website that is inactive or has no description, and a use case titled `Test` or `[TEST] …` are left out; an active startup with a description and a `test.com` website keeps its record without the website. Startups sharing a registrable domain or a normalised name are reported as possible duplicates, not merged. A value with no code is reported, not stored as free text. The v1 `Source` column and company type are counted in the report only.
7. **Files are fetched only from v1 and Google.** The script fetches from `https://papi.genaifund.ai/attachments/` and the use cases' `/use-cases/attachments/` paths on the same host alone, one at a time with a timeout and one retry, checks the type the bytes are (v1 answers `application/octet-stream`) and the size each purpose allows, and reports a file that fails without stopping. A logo becomes the organization's, the customer deck, else the pitch deck, the solution's deck; a demo stays a link, https only. A file on Google Drive, Slides or Docs is fetched by its public download or PDF export address, following redirects only to Google's download hosts; one that is not public, is not a file of the kind, or sits behind Drive's virus-scan page is reported, never bypassed. A folder, a page and a broken link are counted and not fetched.
8. **The report is the reconciliation.** Each run writes the counts read, written, left out and why, and the possible duplicates. Its counts go on Linear; the full report, which names companies, stays with the workbook.
9. **A budget keeps its currency.** 32 use cases of v1 are priced "VND 200M". `use_case.currency` is `USD` or `VND` and the amounts are whole units of it, so nothing is converted on the way in. The public list orders budgets by their value in dollars at `beyondpilot.usecase.vnd-per-usd` and never shows that value; a card writes đồng in millions (`VND 200M`), as Vietnamese budgets are said. Approved in Figma, section `Use case budget — currency`.
10. **What the old records leave empty stays empty.** A company size band of v1 that straddles two of BeyondPilot's stays unknown. An organization's email domain stays empty, so nobody joins an unreviewed organization by their address; the accepted domains of v1 are reported only. The organization's description is the brief description cut to the 280 characters a profile takes, and the solution's summary keeps it whole. A use case takes its problem statement, target users, expected outcomes, current solutions, data readiness and integration requirements from the headed sections of its v1 content, the problem statement and the expected outcomes falling back to its description; the timeline and current process, which v1 does not give, stay empty for the operator.
11. **The same export gives the same rows.** Every identifier is a UUID version 5 of the v1 identifier, and a second load of the same export is refused before it writes anything. An address already taken in the target database takes the next free number, as the backend does.
12. **An approved use case needs its problem, outcomes, industry and budget.** Most v1 briefs lack a timeline in weeks and many lack data readiness, integration or technologies, so `V52` asks only for title, problem statement, industry, expected outcomes and a budget once a use case leaves draft; the rest and the close date may be empty, and a use case with no close date is open with no deadline. An organization sending its own use case through the wizard still has to complete every part. Read-only views of an approved use case leave out what was never written.
