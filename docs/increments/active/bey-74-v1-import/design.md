# Import from the old platform

Status: in progress, 7 October 2026. Tracked in [BEY-74](https://linear.app/beyondpilot/issue/BEY-74) (startups) and [BEY-75](https://linear.app/beyondpilot/issue/BEY-75) (use cases). It carries out the [migration from v1](../bey-22-phase-1-domain-model/design.md#migration-from-v1) of BEY-22 against the real export, and uses the [review lifecycle](../bey-76-review-lifecycle/design.md).

## Source

GenAI Fund's export `genai_matching_db_export_2026-10-04-2.xlsx`, two sheets, each with a title, a record note and a source note above the header on row six:

| Sheet | Records | Holds |
| --- | --- | --- |
| Startups | 2,426 (2,125 active) | Company facts, product fields, links to decks, demos and logos on `papi.genaifund.ai` |
| Use Cases | 233 (218 approved) | Title, description, content, tags, price, deadline, the enterprise's id, name and industry, the creator, links to attachments |

The file holds names and email addresses, so it is never committed. It has no users, proposals or matching decisions. The attachment links answer without a session.

## The full export

On 12 October 2026 GenAI Fund shared `genai_platform_full_db_export_2026-10-08.xlsx`: 13 sheets named as the tables of the old database, passwords redacted. Its `startups` and `use_cases` are cell for cell the two sheets above. It adds the enterprises' profiles (340), the people and the company each belongs to (2,058), proposals and their files, the enterprises' likes, saves and dislikes, the old AI's picks, votes, threads and tags. [BEY-147](https://linear.app/beyondpilot/issue/BEY-147) loads the profiles and the people, in small steps; decisions 14 to 16 below are its own. The rest is not loaded: the likes, saves, dislikes and picks measure matching only, and proposals get their own design.

## Decisions

1. **A one-off load, not a feature.** The brief asks for a migration that reconciles with its source (§11), not for an import function; the export it asks for (§7.10) is operational reporting and comes separately. The records are written once, so the application gains no import module, endpoint or operator method that would have to be removed after the cutover.
2. **A script writes the database.** `infrastructure/legacy-import/` reads the workbook, maps the values, fetches the files and writes one SQL file and a folder of files. Its rules are code in the repository; the workbook, the SQL and the files it produces are not. The SQL runs in one transaction under the database's constraints; the search index is then rebuilt from Admin › AI, since no event is published. The audit log records nothing of the load: its catalog is closed, and an action it does not know would break the log's reading; the dump taken before the load and the build's report record it instead.
3. **Imported, not approved.** GenAI Fund has not said how it wants the old records reviewed (BEY-41), so an organization and an active startup's solution arrive `in_review`, an inactive startup's solution and every use case arrive `draft`. A solution is not listed. An organization has no member and is created by the operator account of the environment. Nothing imported is public until an operator approves it. On staging alone, `staging_list.py` then approves the organizations and approves and lists every imported solution, so matching is built and tried on real data (Đạt, 7 October 2026); production keeps them in review.
4. **Staging first, then production.** The load runs on staging; test records and duplicates are removed there with SQL that is kept with the script. Production receives the same load and the same removals, after a dump of its database.
5. **A use case belongs to programs.** 167 use cases carry a program tag in v1. `usecase` stores `use_case_program (use_case_id, program_id)` and depends on `program`; an operator sets a use case's programs, and the public list narrows by program, so a program page reads its use cases from `usecase` and `program` does not depend on `usecase` ([brief §9](../../../brief/BeyondPilot-Vendor-Product-Brief-and-Scope.md#9-example-operating-scenario): a campaign has linked use cases). This is the one change to the application. Nestlé Vietnam AI Reinvention, which only v1 names, is created as a draft program; its details wait for GenAI Fund.
6. **Map codes; retain the v1 company's descriptive claims.** Solution types map to focus areas, industries to industry codes, product stage to maturity and country names to ISO codes. `|||` and comma lists split; empty strings and "Not specified" become null. Test startups, test-only websites on inactive or undescribed startups and use cases titled `Test` or `[TEST] …` are left out; active startups with a description keep their record without a `test.com` website. Possible duplicates are reported, not merged. Values without a code are reported rather than guessed. The v1 `Source` column and company type remain report-only.
7. **Files are fetched only from v1 and Google.** The script fetches from `https://papi.genaifund.ai/attachments/` and the use cases' `/use-cases/attachments/` paths on the same host alone, one at a time with a timeout and one retry, checks the type the bytes are (v1 answers `application/octet-stream`) and the size each purpose allows, and reports a file that fails without stopping. A logo becomes the organization's, the customer deck, else the pitch deck, the solution's deck; a demo stays a link, https only. A file on Google Drive, Slides or Docs is fetched by its public download or PDF export address, following redirects only to Google's download hosts; one that is not public, is not a file of the kind, or sits behind Drive's virus-scan page is reported, never bypassed. A folder, a page and a broken link are counted and not fetched.
8. **The report is the reconciliation.** Each run writes the counts read, written, left out and why, and the possible duplicates. Its counts go on Linear; the full report, which names companies, stays with the workbook.
9. **A budget keeps its currency.** 32 use cases of v1 are priced "VND 200M". `use_case.currency` is `USD` or `VND` and the amounts are whole units of it, so nothing is converted on the way in. The public list orders budgets by their value in dollars at `beyondpilot.usecase.vnd-per-usd` and never shows that value; a card writes đồng in millions (`VND 200M`), as Vietnamese budgets are said. Approved in Figma, section `Use case budget — currency`.
10. **What the old records leave empty stays empty.** A company-size band that straddles two of BeyondPilot's stays unknown as the normalized `team_size`; its exact v1 label is kept separately as `company_size_label` and shown on the public company block, without guessing a different band. An organization's email domain stays empty, so nobody joins an unreviewed organization by their address; accepted domains of v1 are reported only. The organization's description is the brief description cut to the 280 characters a profile takes, and the solution's summary keeps it whole. A use case takes its problem statement, target users, expected outcomes, current solutions, data readiness and integration requirements from the headed sections of its v1 content, with problem statement and expected outcomes falling back to its description; the timeline and current process, which v1 does not give, stay empty for the operator.
11. **The same export gives the same rows.** Every identifier is a UUID version 5 of the v1 identifier, and a second load of the same export is refused before it writes anything. An address already taken in the target database takes the next free number, as the backend does.
12. **An approved use case needs its problem, outcomes, industry and budget.** Most v1 briefs lack a timeline in weeks and many lack data readiness, integration or technologies, so `V53` asks only for title, problem statement, industry, expected outcomes and a budget once a use case leaves draft; the rest and the close date may be empty, and a use case with no close date is open with no deadline. An organization sending its own use case through the wizard still has to complete every part. Read-only views of an approved use case leave out what was never written.
13. **Public AI solution details preserve their source and review boundary.** Product names, core technology, stack, infrastructure, segment focus, notable paying customers, company use-case industries and descriptions, monetization, company funding and competitors stay distinct fields; `Key Milestones` populate `traction`, not notable customers. Notable customers, funding and alternatives remain company-stated, not reviewed customer deployments. Company-stated use-case descriptions are not rows from the separate enterprise `Use Cases` sheet. Company funding is distinct from operator-written `backing.funding`. The public response includes these fields only for an approved solution with an approved organization. `build.py` writes `v1-details.sql` to refresh these fields on deterministic rows from an older load, without repeating its duplicate-protected inserts.
14. **An enterprise's profile fills what is empty.** The use cases' sheet named an enterprise by its name and industry alone, so its organization had nothing else. `enterprises.py` reads the `enterprises` sheet and completes the organization with the same identifier: website, country, team size with its v1 label, description cut to 280 characters, founding year, and industries where there are none. It overwrites nothing, so what an operator or a member wrote since stays, and a second run changes nothing. A website written without a scheme gets `https://`; one that is not an address is left out. A headquarters that is a city ("Zurich") is not guessed into a country. v1's bands from 5,000 employees up are BeyondPilot's largest; "Less than 100 Employees" straddles three bands and keeps its label only. An enterprise with no organization here is left alone in this step.
15. **An enterprise with people gets its organization, unless one is here already.** Only the enterprises with a use case had an organization. The people of the others can be invited only to an organization that exists, so each enterprise that has people and no use case gets one, in review, with no member, created by the operator account. One with neither people nor a use case gets none: nobody needs it. An enterprise whose name, read as `mapping.normalised_name` reads it, or whose own website domain an organization already has is not created, and its people get no invitation; the load lists them for an operator. Most are companies registered on v1 both as a startup and as an enterprise. Of two v1 records of one company the one with more people is created, since the load meets it first.
16. **An enterprise's logo follows the rules of the startups' files.** `enterprise_logos.py` fetches the logos the `enterprises` sheet names from v1 and Google alone (decision 7) and names each on the enterprise's organization only when that has no logo, so a logo found since by the enrichment or uploaded by a member stays. A file no organization took is removed from storage again.
17. **A person of v1 gets in by accepting an invitation.** The imported organizations have no member, so a founder who signs in finds nothing of theirs. The `representatives` sheet says who belonged to which company. `people.py` writes, for each person of a startup or an enterprise, an operator's invitation to the organization the load made: the organization module already shows an invitation to whoever signs in with its address, and an operator's stays out of an organization's limits. Nobody gets an account, no email is sent, and the invitation is given a hundred years so that it does not lapse. Only a person who is surely the company's is invited: one whose address is on the company's own website domain (Đạt, 12 October 2026: "whoever is not sure is not invited"). On v1 GenAI Fund's staff registered as the representative of client enterprises, and a founder's address on a public mail service may be anyone's today, so an address on a public mail service or on another domain gets none, and neither does a company with no website of its own; a quarter of the people are left out this way. v1 had no owner of a company: of the people invited, the only one of a company is invited to own it; of several, the one whose position or job title says founder, owner or chief executive is, the earliest to register when there are several or none, and the others are invited as members; an organization somebody owns or is invited to own already takes everyone as a member. The people of an enterprise that decision 15 did not create are invited as members to the organization that stands for it: the one that has the enterprise's website, or the one that has its name when the person's address is on that organization's website. An address that already belongs to an organization gets none, since a person belongs to one. An operator's address gets none: an operator runs the platform and does not own a company's profile through the load (Đạt, 12 October 2026). An account that has signed in and belongs to no organization is invited: a founder who came back is the person the invitation is for. A person who signs in with another address uses the claim request that exists.
18. **A company the old platform holds twice becomes one organization.** Decision 6 reported possible duplicates and merged none; on staging that left 131 groups of organizations with one name, 94 of them with one website too, and one company could show twice in a use case's matched solutions. Duplicates are not left in the data (Đạt, 12 October 2026; [BEY-156](https://linear.app/beyondpilot/issue/BEY-156)). `duplicates.py` merges the organizations that are surely one company, those with one name read without its legal form and one website, by SQL that does what `OrganizationAdministration.merge` and the modules listening to `OrganizationMerged` do, since the load has no operator session to call them with: open invitations and requests, solutions, offers, use cases, proposals, introductions and enquiries move to the kept organization, and the duplicate stays with the status `merged` and where it went. A change to what a merge moves in the application must be made in this file too while it is still to be run on production. The kept one is the one whose solution has a deck, then the one active on v1, then the fuller record, then the one updated last on v1. The solutions with one name under the kept organization are one product described several times, since a company that registered twice wrote itself up twice: the best by the same order stays and the others are refused with the reason `duplicate`, the state the review already has for this, with a message that names the record kept; nothing is deleted, and a wrong choice is put right by reviewing the solution again. Taking a duplicate off the list was tried first on staging and does not do: search and matching read an approved solution listed or not, so the duplicates came back in the next matching run. A matching result on a refused solution is removed, unless a person decided or answered on it. A group in which an organization has members is left for a person, since a merge moves people and tells them by email, and so is one whose keeper is not approved. Groups with one name and different websites are not merged by rule. Production runs this before or with its load, so that it never holds the duplicates.
