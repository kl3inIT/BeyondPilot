# Proposal: verification matrix

Boundaries follow [conventions › Testing](../conventions.md#testing). An application is written over several requests, checked against a program's questions and the clock, and kept as versions, so the proposal tests start the full application against PostgreSQL and speak real HTTP. Sign-in goes through the real code flow with the SMTP server replaced; a stored file is a row of `storage_file`, since a save reads the record, never the bytes.

Not covered by a test: two tabs saving the same application at the same moment. The row is locked for the save and the version decides; the second is told it changed.

## The screens

`web/tests/e2e/apply.spec.ts` runs on desktop and mobile Chrome with axe. The web server's reads are answered by `tests/e2e/stub-applications.mjs`; what the browser writes is answered by the test, which keeps the application, the organization and the solution between calls. It covers: signing in comes first and returns to the form; step 1 says beside each field what is missing and focuses the first; a person on their own applies through an organization made from their name; the solution is saved and its deck uploaded at once; the program's questions, a file among them; the review shows everything and asks for a confirmation before the submission; the receipt, My applications and an application's page; withdrawing asks first and sends one command; My applications starts empty and leads to the programs.

Set `APPLY_SHOTS` to a folder to save a screenshot of each step at both widths.
