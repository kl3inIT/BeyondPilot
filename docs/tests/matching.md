# Matching: verification matrix

Boundaries follow [conventions › Testing](../conventions.md#testing). What code makes of a model's answer is plain code and is tested without a model or a database. What is kept is PostgreSQL's work and is tested through the repository. A whole run is tested against PostgreSQL with the organization, the solution and the use case made over HTTP the way people make them, and the model played by the JDK's `HttpServer`; no test calls a real provider.

The search that finds the candidates is in the [search matrix](search.md).

Not covered by a test: the Matching settings page in Vietnamese, its question before leaving with unsaved numbers, and a save that fails for a reason other than a changed version; the Matched solutions page while a run is queued, waits or failed, without a model, and before the first run; the stream through the real reverse proxy, which is watched on staging; the heartbeat every 20 seconds; the stream asked for again after the browser gave up on it; the motion of a row that enters its group (the browser tests run with reduced motion); a stream left open by a session that ended; the page in Vietnamese; the 44px touch targets; the Undo of a removal; reading the pages of a file attached to a use case (the page reader is covered in the [AI matrix](ai.md)); the worker's schedule itself, since the test takes each run; more than two solutions read at once, and that a run at work keeps the limits it started with; the quality of the wording itself, which no test with a played model can show: it is measured on real use cases through the real provider ([prompt research](../research/2026-10-09-matching-judge-prompts.md)).
