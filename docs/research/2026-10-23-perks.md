# Perks: Builder Hub's model and how perk programs work elsewhere

Studied on 23 October 2026, after Kai Yong asked Joshua Si for "the perks details (what you used to build builder hub)" so the team could "update for our solutions part" of beyondpilot.ai. Joshua described a perk the same morning (steps and terms; a claim type such as forms, voucher codes or sign-ups; active and end dates; some perks only for the shortlist or winners, some only for registrants of a program, some for everyone) and sent `builder-hub-perks-schema.xlsx`, his workbook of Builder Hub's schema, rules, API and a production snapshot of 22 October. The workbook is not kept in the repository; what it says is below. Tracked in Linear as BEY-247.

## Builder Hub

### The model

From the workbook, prepared from the Builder Hunt repository on 22 October 2026:

| Part                | What it holds                                                                                                                                                                                                                                                                                                                                                                                          |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `perks`             | One record per perk: slug, title, blurb, `value_label`, logo, the owning organization, `eligibility_type` and its configuration, `claim_scope` (`per_product` or `per_builder`), `quantity` (null is uncapped), `expires_at`, `terms_url`, `lifecycle_state` (draft, published, archived), rich-text about, eligibility callout and terms, ordered instruction steps, `cta_type` and its configuration |
| Eligibility         | `registered_with_draft`, `launched`, `shortlist`, `top_five`, `winner`, `everyone`, `custom`                                                                                                                                                                                                                                                                                                           |
| Ways to claim       | Current organization perks: `direct_link` or `builder_hub_form`. `code` and `manual_approval` remain on legacy records only                                                                                                                                                                                                                                                                            |
| Availability        | Computed on read: `available`, `out_of_stock` (a finite quantity reached by active submissions), `expired` (`expires_at` passed). Expired and out-of-stock perks stay discoverable at lower priority and cannot be used                                                                                                                                                                                |
| Submissions         | `organization_perk_submissions`: perk, organization, user, campaign, product, answers, status `submitted` → `fulfilled`, `rejected` or `expired`, an operator note, idempotency keys. Private to the submitter, the organization and admins; exported as CSV                                                                                                                                           |
| Campaign placements | A published perk is placed in one or more campaigns with an order; removing a placement leaves the campaign's partner relation alone                                                                                                                                                                                                                                                                   |
| Who publishes       | Members of the owning organization create, save, publish and archive their own perks. Publishing checks only that the structured content is complete. Admins manage every perk. Logos alone are moderated (`perk_media` must be scanned, approved and ready before it is public)                                                                                                                       |
| Language            | The UI says perk, submission, sign-up and request; "claim" stays only in legacy tables and routes                                                                                                                                                                                                                                                                                                      |
| Legacy              | `perk_claims`, `perk_providers`, `perk_page_blocks`, `campaign_perks` and `editor_mode` are kept for compatibility with the campaign-owned model of migration 0058, which migration 0063 replaced with standalone perks                                                                                                                                                                                |

Routes: `/perks` and `/perks/:slug` for the public; `/dashboard/organizations/perks` for an organization; `/admin/perks` for admins; `/my/perks/submissions` for a person's own submissions.

### The data

The public API (`/v1/perks?limit=48&sort=title_asc` and each perk's detail) was read on 11 October and again in the workbook's snapshot of 22 October: 34 published perks, 14 available, 20 expired (the AI Talent IDX campaign's), none out of stock.

| Of the 14 available               | Count | Perks                                                                                                                      |
| --------------------------------- | ----- | -------------------------------------------------------------------------------------------------------------------------- |
| Everyone, a link                  | 12    | AWS credits, Apollo, Brevo, ElevenLabs, Gamma, Instantly.ai, Kit, Netlify, Notion, Quo, Softr, TinyFish Ambassador Program |
| Everyone, a form                  | 1     | OpenAI credits + ChatGPT Plus: three questions (OpenAI email, name, organization ID), fulfilment `automatic`               |
| A campaign's participants, a form | 1     | UnifyAPI's Builder API Gateway                                                                                             |

No available perk uses `shortlist`, `top_five` or `winner`; the expired ones are not served in detail. Every detail read has `submissionScope: per_builder`. Several value labels are sentences ("$10 launch credit for eligible teams") rather than amounts.

| Hackathon sponsors                        | Credits go to every participant who submits (HackerNoon's Proof of Usefulness) or as prizes to winning teams                                                                                                                        | [HackerNoon](https://hackernoon.com/everything-you-need-to-know-about-hackernoons-proof-of-usefulness-hackathon), [MLH guide](https://guide.mlh.io/general-information/getting-sponsorship/potential-sponsor-perks) |

Codes: vendors of code tools advise a single-use code per recipient for anything of value, since a leaked shared code is used by anyone, and a shared code only for broad public campaigns. A determined person can still claim twice with another address, so a limit per account or company and an expiry go with it ([Uniqodo](https://www.uniqodo.com/post/unique-vs-generic-voucher-codes), [Uniqodo on abuse](https://www.uniqodo.com/post/promo-code-abuse), [Awin](https://help.awin.com/docs/protect-your-program-against-unauthorised-voucher-codes), [ReferralCandy](https://help.referralcandy.com/en/articles/2457786-other-platforms-why-isn-t-there-an-option-for-single-use-coupon-codes-for-the-friend-offer)). Most of these sources sell such tools.

Approval: Luma has a "Require approval" switch per event ([registration process](https://help.luma.com/p/event-registration-process)); Builder Hub's form has a fulfilment mode, automatic for OpenAI's.

## What follows

1. A catalogue anyone can read, opened by membership: who a perk is for is public, a code, a private link or a form opens only to those who qualify.
2. Programs for startups count a perk per company; programs for individuals count per person. Builder Hub counts per builder because its users are individual hackathon builders.
3. A member sees again what they got (Builder Hub, Devfolio, the fund platforms).
4. Single-use codes for a perk of value; a shared code only where its leaking costs little.
5. Builder Hub publishes an organization's perk without review and keeps an expired one reachable.

The decisions taken from this are in the [perks increment](../increments/active/bey-247-perks/design.md).
