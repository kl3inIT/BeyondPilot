# What Payload teaches an App Router application

Written on 4 October 2026. Payload is the one reference built like this application: Next.js App Router with Server Components. The others (the Medusa admin, MemoryOS, Dub) run their admin in the browser. This note records what was read in Payload (`4.0.0-canary.37`, cloned under `.tmp/payload`), what transfers, and where each lesson lands. Nothing was run; every finding is from reading source. Paths are relative to the Payload repository.

The difference that decides what transfers: Payload's data layer runs inside the Next.js process, and its screens are generated from collection configuration. Here the data is behind a separate Spring API, writes go from the browser to Spring, and screens are written by hand. A pattern that depends on in-process hooks, Server Actions as the write path or configuration-driven fields does not transfer; the idea behind it often does.

## Does not transfer

- Form state computed on the server from field configuration, and fields rendered by the server.
- The access evaluation engine. The idea of one compact permissions document per request does, when roles become finer than `user` and `operator`.
- Revalidation called from hooks inside the process, and reads through the in-process data layer in Server Components.
- Server Actions as the way to write: here writes go to Spring ([ADR 0002](../decisions/0002-nextjs-frontend-over-the-spring-backend.md)).
- Version storage, locks and preferences as code. The patterns are above; the code belongs to Spring.

## Not found

- An error boundary in Payload's interface packages, a skip link, and a handler for a session that ends during a submit.
- Progress by bytes during an upload.
- Whether the published copy lives in the main table while drafts live only in versions: assumed from the start of `replaceWithDraftIfAvailable`, not confirmed.
