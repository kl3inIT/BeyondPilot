## Different choices here, and why

| Their choice                                                                                           | Here                                                                                                   | Reason                                                                                                                                                                                                                          |
| ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| odd-platform mirrors into the unified index with **database triggers**, so no write path can forget it | **Events** published by each module's service                                                          | A trigger on `solution` or `talent` would be one module writing from another module's tables, which the module boundaries forbid. The registry, a nightly comparison and a full rebuild cover what a forgotten event would miss |
| odd-platform checks **eligibility at read time** by joining the index back to the base tables          | **Only public items enter the index**; an item that stops being public is removed                      | The join crosses module tables. Keeping private items out also means a mistake in a query cannot show a draft                                                                                                                   |
| odd-platform and persistent-agent-runtime use the **database default or `english`** text configuration | **`simple` with an immutable `unaccent`**                                                              | Vietnamese has no PostgreSQL stemmer, and English stemming mangles Vietnamese words; unaccent lets "viet nam" find "Việt Nam"                                                                                                   |
| Neither uses **`pg_trgm`**                                                                             | **Trigram on names**                                                                                   | People type partial and misspelled names of companies and products. GitLab uses trigram indexes for the same reason ([blog](https://about.gitlab.com/blog/fast-search-using-postgresql-trigram/))                               |
| persistent-agent-runtime embeds **once, with no model recorded and no re-embedding**                   | **Model, dimensions and content hash stored per vector**, with a batch job that re-embeds what changed | BEY-21 is still choosing the model; changing it later must not need a migration                                                                                                                                                 |
| MemoryOS runs **OpenSearch with Redis dispatch, chunking and access tokens**                           | **PostgreSQL only, one row per item**                                                                  | A few thousand short public items; no chunking or per-document access is needed                                                                                                                                                 |

What it settles:

- **The layout follows the cardinality.** Every codebase with one text, one vector and one current model keeps the vector on the row; every one that splits text into chunks or keeps several models side by side uses a separate table. `search_document` has one card per item and one model at a time, the case pgai's column mode is made for, and it is already the side table that Immich's `smart_search` is to its assets. The one-table choice stands.
- **Its cost is a model with other dimensions.** The `vector(n)` column then needs a migration and every row is re-embedded; until a row is, its old vector must not be compared with the new model's, so the vector branch filters `embedding_model` to the current model, as rag-pipeline's `VectorRetriever` does.
- **Stale detection is a hash of the embedded text beside the vector** everywhere: Discourse's `digest` (SHA1 of the prepared text, `lib/embeddings/vector.rb`), Supabase's page `checksum`, rag-pipeline's `fingerprint` with the model in it. `embedded_hash` against `content_hash` is the same idea.
- **A provider outage is a state of the provider, not of each row.** Discourse pauses a model in Redis for 30 s, 3 min, 20 min, 1 h, then 6 h after a terminal error, and for `retry_after` after a rate limit (`lib/embeddings/provider_health.rb`); jobs skip while it is paused and the backfill catches up. pgai keeps retries per queued row. Here the job stops its batch at the first provider failure and waits, so an outage charges no row; the per-row attempts and error only hold back an item the provider rejects on its own, such as a text it refuses.
- **Visibility is filtered inside the vector query, with room to spare.** Discourse sets `SET LOCAL hnsw.iterative_scan = relaxed_order`, takes twice the limit and re-ranks, and over-selects four times for filters applied later (`lib/embeddings/schema.rb`, `semantic_search.rb`); LangChain4j puts the filter in the `WHERE` of both branches before the `LIMIT`.
- **RRF in SQL is common, with k between 50 and 60.** LangChain4j and Supabase fuse with a full outer join; Supabase uses k = 50 with a weight per branch, LangChain4j and Discourse's discoveries 60. Discourse runs both branches and answers with one when the other fails.
- **Measuring relevance.** rag-pipeline keeps a golden set of 41 questions, drafted so they do not copy the text they should find, labelled by source rather than chunk id, and reports hit@5, recall@5, MRR@10 and latency (`eval/RetrievalMetrics.java`, `eval/README.md`). The AI slice needs the same before it changes a weight.
- **Writing a vector after a model change.** Immich skips the write when the model changed while the item was being encoded (`handleEncodeClip` in `smart-info.service.ts`); writing `embedded_hash` with the vector gives the same safety here, since a row embedded from old text stays stale.

## Does not transfer

- Database triggers or joins across module tables (odd-platform).
- Redis, OpenSearch, chunking, generations and per-document access tokens (MemoryOS).
- Tenant and agent scoping, and the hand-written HTTP client for embeddings (persistent-agent-runtime); Spring AI's `EmbeddingModel` replaces the client.
- Republishing incomplete events on every restart when more than one instance runs; with one instance it is safe, otherwise a single scheduled resubmission.
